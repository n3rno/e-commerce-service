# 카프카
대규모 실시간 데이터 스트리밍을 위한 "분산 메세징 시스템"

## 카프카의 구성요소
#### 프로듀서 (Producer) - 메세지를 카프카 브로커에 적재(발행)하는 서비스
#### 컨슈머 (Consumer) - 카프카 브로커에 적재된 메시지를 읽어오는(소비) 서비스
#### 오프셋 (Offset) - 컨슈머가 어디까지 메시지를 읽었는지를 기록해둔 데이터

#### 브로커 - 카프카 클러스터를 구성하는 물리적인 서버들
- 프로듀서에게 메시지를 받아 이를 저장하고 이를 컨슈머로 전송하는 역할

#### 메시지 - 프로듀서에서 컨슈머로 이동하는 데이터.
- Key(리소스Id), Value(리소스 상세정보)로 구성되어 있다.

#### 토픽 - 메세지를 분류하는 기준. n개의 파티션으로 구성되어있다.
#### 파티션 - 실제 메시지가 담겨있는 큐.
- <span style="background-color:#fff5b1">대용량 트래픽</span>을 파티션의 개수만큼 병렬로 처리할 수 있어 <span style="background-color:#fff5b1">빠른 처리</span>가 가능하다.
- 전체 메세지의 발행 순차처리를 보장하지 않지만, 같은 파티션의 메세지에 대해서는 순차처리를 보장한다.
- 하나의 파티션은 하나의 컨슈머만 사용할 수 있다. 
- 메시지가 어떤 파티션에 담길 지는 메시지의 키값에 따라 결정된다.

#### 컨슈머 그룹 - 토픽에 있는 메시지를 구독하는 단위.
- 보통 하나의 서비스를 나타낸다. 

#### 리밸런싱 - 특정 컨슈머로부터 다른 컨슈머로 파티션의 소유권을 이전시키는 행위.
    리밸런싱 중에는 컨슈머가 메시지를 읽을 수 없다. 

#### 클러스터 - 고가용성과 확장성을 위해 여러 브로커(서버)를 묶어 하나의 시스템으로 구성한 것.
- 동작중인 다른 브로커에 영향없이 확장이 가능하다.
  - Broker가 증가할 수록 메시지 수신, 전달 처리량을 분산시킬 수 있다.

#### 레플리케이션 - 브로커 중 하나에 갑자기 장애가 생겼을 때, 다른 브로커에 복제본(Replica)을 만들어두는 기능.


-----------------------
### Kafka에서 <span style="background-color:#fff5b1">메시지 순서 보장과 처리량을 동시에 확보</span>하기 위해 어떻게 설계해야 할까?
순서 보장의 기준이 되는 값을 메시지 키로 설정하고, 토픽의 파티션 수를 늘려 병렬 처리를 극대화한다. 

-----------------------
### Kafka를 활용한 시스템에서 장애나 <span style="background-color:#fff5b1">메시지 유실 방지</span>를 위해 어떤 전략을 사용할까?
Kafka는 Replication 기능을 기본적으로 제공하여 특정 브로커에 장애가 생겨도 
다른 브로커가 장애가 발생한 브로커의 역할을 즉시 대신할 수 있도록 하는 매커니즘이 적용되어 있다.

또한, Offset Commit 개념을 통해 컨슈머가 메시지를 ‘최소 한 번 이상 처리(At-Least-Once)’할 수 있도록 하며 
메시지를 처리하는데 문제가 계속해서 발생하는 경우 DLQ를 활용하여 Fallback 프로세스를 구성할 수 있다.

### 실제 운영과 관련된 심화 주제
1. Auto-commit vs Manual-commit
   - Auto-commit: 카프카 컨슈머가 기본적으로 default 5초마다 현재까지 처리한 메시지의 오프셋을 자동으로 커밋하는 방식
     - 데이터 유실 가능성이 있다. 
     - 데이터 중복 처리 가능성이 있다.
     - 실전에서 잘 쓰이지 않는 방식
   - Manual-commit: 개발자가 코드 내에서 직접 오프셋을 커밋하는 방식
     - `commitSync()`: 안정적이지만 성능 저하 발생 가능성 있음.
     - `commitAsync()`: 처리량 우선 시 유리하지만, 커밋 실패에 대한 추가적인 오류처리 필요.

2. DLQ (Dead Letter Que)
    - 컨슈머가 재시도해도 처리할 수 없는 문제 있는 메시지를 모아두는 전용 토픽.
    - 카프카 기반 시스템의 안정성과 견고함을 높이는데 필수적인 패턴이다.
    - 활용
      - 모니터링: DLQ에 쌓이는 메시지들을 모니터링하여 어떤 종류의 오류 메시지가 발생하는지 파악하고, 근본 원인을 분석
      - 재처리: 오류의 원인이 해결된 후, DLQ에 쌓인 메시지들을 수동으로 또는 별도의 프로세스를 통해 다시 정상 토픽으로 보내 재처리
      - 격리: 문제 있는 메시지가 다른 정상적인 메시지의 처리를 방해하지 않도록 격리

3. 리텐션(Retention) 정책
   - 카프카 브로커는 메시지를 한 번 저장하면, 컨슈머가 메시지를 소비했는지 여부와 관계없이 
   일정 기간 동안 메시지를 보관한다.
   - 목적
     - 컨슈머 장애나 버그 발생 시, 과거의 메시지를 다시 읽어 재처리 할 수 있도록 하기 위함.
     - 새로운 컨슈머 그룹이 구독을 시작할 때, 과거 데이터부터 읽을 수 있다.
   - 설정 기준
     - 시간 기반(Log Retention Time): 메시지가 발행된 시점으로부터 특정 시간(ex 7일)이 지나면 삭제.
     일반적으로 사용하는 정책이다.
     - 크기 기반(Log Retention Size): 토픽의 파티션 크기가 특정 크기 (ex 1GB)를 초과하면 
     오래된 메시지부터 삭제

4. 멱등성(Idempotency)
   - 멱등성: 동일한 연산을 여러번 수행하더라도 결과가 항상 동일하게 유지되는 특성
     - 카프카는 메시지 전달을 최소 한 번 (At-Least-Once) 보장한다.
     - 즉, 같은 메시지가 여러 번 전달 될 수 있다.
       - -> 만약 멱등성이 보장되지 않는 작업을 여러번 수행하면 시스템에 예상치 못한 부작용이 발생할 수 있다.
   - 예시
     - 비멱등적(Non-Idempotent) 연산: '계좌에서 100원 차감'이라는 메시지를 여러번 받으면 계좌 잔액이 계속 줄어들 수 있다.
     - 멱등적(Idempotent) 연산: '주문상태를 "결제완료"로 변경' 메시지를 여러번 받아도 
       주문 상태는 최종적으로 "결제완료"로 동일하게 유지되는 경우.
   - 멱등성 확보 방법
     1. Unique Id 활용: 메시지마다 유니크한 ID(ex UUID)를 부여하고, 
     컨슈머는 이 ID를 기준으로 이미 처리된 메시지인지 확인하여 중복 처리를 방지한다.
        - db에 `processed_message_id` 테이블을 만들고, 메시지 ID를 저장 후 조회한다.
     2. 상태 기반 처리: 특정 상태로의 전환만 허용하거나, 최종 상태를 덮어쓰는 방식으로 처리한다.
        - ex) '결제대기'에서 '결제완료'로만 변경 가능하게 하거나, 주문 상태를 단순히 '결제완료'로 업데이트 한다.

5. Zero-Payload vs Full-Payload
`카프카 메시지에 얼만큼의 데이터를 담을 것인가`
    - Full-Payload (풀 페이로드)
      - 메시지에 필요한 모든 데이터를 직접 담아서 발행하는 방식
      - ex) 주문 완료 이벤트 메시지에 주문 번호, 상품 목록, 결제 금액, 배송지 주소 등 모든 주문 정보를 담는 경우
    - Zero-Payload (제로 페이로드)
      - 메시지에는 최소한의 식별 정보(ID)만 담고, 필요한 실제 데이터는 별도의 데이터 스토어(DB, Redis 등)에서 조회하도록 하는 방식
      - ex) 주문 완료 이벤트 메시지에 주문 번호(orderId)만 담고, 컨슈머는 orderId를 이용해 DB에서 주문 상세 정보를 조회하는 경우
    - 실무에서는 Zero-Payload가 더 많다.
      - 데이터 무결성 및 최신성: 메시지가 발행된 시점의 데이터가 아니라, 컨슈머가 메시지를 처리하는 시점의 가장 최신 데이터를 조회해야 하는 경우가 많다.
        - Full-Payload 방식은 메시지 발행 시점의 스냅샷 데이터이므로, 이후 데이터가 변경되면 메시지의 데이터는 과거의 정보를 담고 있는 문제 발생할 수 있다.
      - 메시지 크기 최적화: 대용량 트래픽 환경에서는 메시지 하나의 크기가 전체 시스템 성능에 미치는 영향이 클 수 있다.
        - Kafka도 무적의 시스템은 아니기 때문에 최소한의 부하를 줘야 클러스터가 안정적으로 운영된다.
      - 데이터 변경의 유연성: 실제 상세 데이터의 스키마가 변경되어도 메시지의 스키마는 거의 변하지 않으므로, 시스템 변경에 대한 유연성이 높다.
      - 역할 분리: 카프카는 이벤트 전달 플랫폼으로서의 역할에 집중하고, 실제 데이터 저장 및 관리는 전용 데이터 스토어가 담당하게 하여 시스템의 책임과 역할을 명확히 분리할 수 있다.
